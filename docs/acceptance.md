# Критерии приёмки

Здесь описано, что и как мы проверяем. Ничего сверх этого на приёмке не
появится — кроме отказов, о классах которых сказано в [task.md](task.md).

## Где что должно открываться

| Адрес                    | Что там                                            | Кто поднимает |
| ------------------------ | -------------------------------------------------- | ------------- |
| http://localhost:8080    | Фронт: форма заказа и список последних заказов      | дано          |
| http://localhost:8000    | API                                                 | дано          |
| http://localhost:8000/docs | Схема API (FastAPI)                               | дано          |
| http://localhost:8001/metrics | Метрики обработчика                            | дано          |
| localhost:5432           | Postgres, база `orders`                             | дано          |
| localhost:9092           | Kafka, топик `orders`                               | дано          |
| http://localhost:9090    | Prometheus                                          | **вы**        |
| http://localhost:3000    | Grafana с дашбордом                                 | **вы**        |

Порты можно менять, если обоснуете и опишете в README.

Фронт ходит в API через префикс `/api/`: nginx проксирует его на
`http://order-api:8000/`. Если вы назовёте сервис API иначе — поправьте
`src/web/nginx.conf`.

Топик `orders` создаётся автоматически при первой отправке, отдельного шага
инициализации не требуется.

## API

```
POST /orders
  {"order_id": "<uuid>", "customer_id": "<str>", "amount": <number>, "items": [...]}
  -> 202 {"status": "accepted", "order_id": "..."}

GET  /orders?limit=50        -> список последних заказов из базы
GET  /orders/{order_id}      -> 200 с заказом либо 404
GET  /health                 -> 200, если сервис готов обслуживать
GET  /metrics                -> метрики в формате Prometheus
```

Пощупать руками:

```bash
curl -s -X POST http://localhost:8000/orders \
  -H 'Content-Type: application/json' \
  -d '{"order_id":"11111111-1111-1111-1111-111111111111","customer_id":"cust-1","amount":990.00,"items":[{"sku":"MILK-1L","qty":1}]}'

curl -s http://localhost:8000/orders/11111111-1111-1111-1111-111111111111
```

## Проверка фронта

1. Открыть http://localhost:8080.
2. Заполнить форму, отправить заказ — страница показывает подтверждение приёма.
3. Обновить список — заказ в нём присутствует.

Ожидание по времени: заказ появляется в списке не позже 60 секунд после приёма
(требование Б4). Обычно — быстрее секунды; 60 секунд это потолок, а не норма.

## Прогон сохранности

Генератор шлёт заказы и пишет журнал отправленного. Чекер сверяет журнал с
базой данных.

```bash
# нагрузка: 50 заказов в секунду в течение 120 секунд
python scripts/load.py --rate 50 --duration 120 --journal data/sent.jsonl

# сверка
python scripts/check.py --journal data/sent.jsonl
```

Вывод чекера:

```
отправлено запросов        6000
принято API (2xx)          5987
найдено в базе             5901
уникальных в базе          5889
-------------------------------
потеряно                     98
дублировано                  12
ИТОГ: ПРОВАЛ
```

Код возврата: `0` — сошлось, `1` — нет.

**Потеряно** — заказы, на которые API ответил успехом, но которых нет в базе.
Это нарушение Б2. **Дублировано** — заказы, встречающиеся в базе больше одного
раза. Это нарушение Б3.

Оба числа должны быть нулевыми: после штатного прогона и после прогона, в
котором мы ломали компоненты.

Скрипты работают на Python 3.11+ локально либо из контейнера — образ описан в
`scripts/Dockerfile.tools`. Подключение к базе берётся из переменных окружения
(см. `.env.example`).

## Порядок приёмки

1. Мы независимо клонируем вашу ветку на свою машину и выполняем
   `docker compose down -v && docker compose up -d --build`. Стенд должен
   подняться без ручных действий и без файлов, которых нет в репозитории.
2. На созвоне вы делаете то же самое у себя, с нуля, при нас.
3. Штатная нагрузка 10 минут: чекер сходится, ни одно правило не сработало.
4. Отказы (классы перечислены в [task.md](task.md)): после каждого — чекер
   сходится, нужное правило сработало и дошло до канала.
5. Разбор решений: механизмы, пороги, что отложено и почему.
6. Блок с ИИ-агентом: 20 минут на добавление новой метрики и правила по ней.

## Обязательный минимум

Всё перечисленное должно выполняться одновременно:

- [ ] стенд поднимается одной командой из чистого клона;
- [ ] заказ проходит путь «фронт → API → очередь → база» и виден в списке;
- [ ] после штатного прогона: потеряно 0, дублировано 0;
- [ ] после прогона с отказами: потеряно 0, дублировано 0;
- [ ] шесть обязательных правил существуют, доставляются в канал и доказаны
      срабатыванием;
- [ ] за 10 минут штатной нагрузки не сработало ни одного правила;
- [ ] `RUNBOOK.md`, `FINDINGS.md`, `AI_LOG.md` заполнены;
- [ ] CI на pull request краснеет, если чекер не сошёлся.
